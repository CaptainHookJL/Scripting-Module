Investigation challenge
=======================
Collected ranking: [('203.0.113.10', 15), ('198.51.100.24', 14), ('198.51.100.77', 8), ('203.0.113.200', 5), ('203.0.113.15', 3)]
Server ranking: [('203.0.113.10', 51), ('198.51.100.24', 37), ('198.51.100.77', 15), ('203.0.113.15', 11), ('203.0.113.200', 10)]
Same top attacker: True. For these actual fixtures the collected log gives the correct top source and top-three order, but understates event counts and omits later activity. This differs from the ranking-change implication in the worksheet.
Complete correctly parsed targeted usernames: [('admin', 39), ('root', 35), ('guest', 18), ('test', 13), ('backup', 13), ('oracle', 5), ('postgres', 1)]
Naive next-word-after-for usernames: [('admin', 39), ('root', 35), ('guest', 18), ('test', 13), ('backup', 13), ('oracle', 5), ('invalid', 1)]
Invalid-user line(s):
Sep 20 09:12:10 server sshd[2002]: Failed password for invalid user postgres from 203.0.113.10 port 51234 ssh2
The naive pipeline counts invalid as a username because it reads the word after for in "for invalid user NAME". The completed report skips invalid user and extracts NAME.
Web log: zero Failed password events, no attacker or targeted usernames; correct for this SSH metric but not meaningful web-threat analysis. A web report should group request source addresses, status codes, paths and suspicious user agents such as sqlmap.
Firewall BLOCK records:
ALLOW 192.168.1.20 -> 10.0.0.10:443
BLOCK 203.0.113.10 -> 10.0.0.10:22
ALLOW 192.168.1.35 -> 10.0.0.20:80
BLOCK 198.51.100.24 -> 10.0.0.10:22
BLOCK 203.0.113.200 -> 10.0.0.30:3389

Possible explanations for blocked SSH sources still appearing in auth.log: (1) authentication events occurred before a block was introduced or on a connection already established; (2) collected firewall and SSH records refer to different hosts/interfaces or traffic paths. The firewall fixture lacks timestamps, so neither hypothesis can be proven from these files.
