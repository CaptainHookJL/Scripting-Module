Layout, usage and interpretation
================================
Run the scripts from lab10. The original worksheet is lab10.md in this folder. Its lab04-data/lab03-data directories correspond to lab04 and root iocs.txt/users.csv in this repository. case and intel are unchanged copies; no collected script or executable was run. The nine exercise scripts share lib/common.sh for input/search checks.
read_csv.sh accepts all (default), disabled or security; find_first.sh optionally accepts a logfile; admin_files.sh optionally accepts a keyword (default admin, or password for Exercise 4.5). check_iocs.sh takes one logfile. Other scripts take no arguments.
scan_all.sh exits 0 for no configured-IOC matches, 1 for an investigation signal, and 2 for an input/search failure. Thus exit 1 in the saved scan is an expected finding, not an execution failure. No matches against a supplied IOC list is not proof a collection is safe. The count is matching indicator entries per log, capped at three per log; repeated list entries would be counted separately. The script waits for the find producer too, so inaccessible traversal is an error rather than a misleading clean scan.

Exercise 1 and Parts 2-3: why line-by-line reading matters
==========================================================
Unsafe loop on test_indicators.txt:
Indicator: [suspicious]
Indicator: [domain.example]
Part 2 word splitting:
Item: [one]
Item: [two]
Item: [three]
Item: [single-word-entry]
Safe line-by-line reading:
Line: [one two three]
Line: [single-word-entry]
Command substitution removes trailing newlines, then unquoted expansion splits on whitespace and can expand globs; a line containing spaces stops being one record. The safe while loop processes one record at a time and preserves spaces/backslashes. Temporary demonstration files were deleted.

$ ./read_firewall.sh
BLOCK from 203.0.113.10 to port 22
BLOCK from 198.51.100.24 to port 22
BLOCK from 203.0.113.200 to port 3389
Blocked records per destination port:
  port 22: 2
  port 80: 0
  port 443: 0
  port 3389: 1
Total BLOCK records: 3
Exit code: 0
Firewall parsing intentionally uses the default whitespace IFS: ACTION, source, arrow and destination are separate fields. With IFS= the entire line lands in ACTION and the other fields are empty:
ACTION=[BLOCK 203.0.113.10 -> 10.0.0.10:22] SRC=[] ARROW=[] DST=[]
The final script prints BLOCK records only and reports two blocks for port 22, one for 3389, and zero for 80/443. These are logged decisions, not proof every connection from those addresses was blocked.

Exercise 4: recursive NUL-safe iteration and persistent counters
================================================================
$ ./lost_count.sh
inside the loop: COUNT=1
inside the loop: COUNT=2
inside the loop: COUNT=3
inside the loop: COUNT=4
after the loop:  COUNT=0
Exit code: 0
$ ./kept_count.sh
case/logs/auth.log: 60 lines
case/logs/firewall.log: 5 lines
case/logs/access.log: 80 lines
case/nested/archive/old.log: 1 lines
after the loop: COUNT=4
Total lines: 146
Exit code: 0
The find scan includes four logs and 146 newline bytes in total, adding case/nested/archive/old.log to the three immediate log files scanned in Lab 9. In lost_count the pipeline loop changes a subshell copy of COUNT, so the parent stays at 0. Process substitution feeds data without moving the loop into a subshell, so kept_count retains both the count and line total. The demonstration explicitly disables Bash lastpipe; that optional setting can otherwise change pipeline behavior in some shells.

Exercise 5: reproduce missing-newline, subshell and read bugs
=============================================================
Original missing-final-newline loop:

[second]

[first]

[third]
Different producer, same lost-counter problem:

An extra separator mismatch was reproduced: find -print with read -d "" processes zero records because newlines are not NUL separators. The final scripts pair -print0/-Z with -d "".


Investigation challenge: saved report, exit status and cap verification
=======================================================================
$ ./scan_all.sh > scan_report.txt
$ echo "Exit code: $?"
Exit code: 1

The final report says Investigation required: yes, so exit 1 correctly signals matches. Four logs were scanned:
case/logs/access.log: 2 full matches, 2 reported; early break=no.
case/logs/auth.log: 3 full matches, 3 reported; early break=yes.
case/logs/firewall.log: 3 full matches, 3 reported; early break=yes.
case/nested/archive/old.log: 0 full matches, 0 reported; early break=no.
Early break triggers for auth.log and firewall.log. check_iocs.sh confirms exactly three matches in each, so this fixture loses no matching indicators, even though some nonmatching IOC entries after the third hit are left untested. A synthetic four-match log was also checked: scan_all stops at three while check_iocs finds four, confirming the cap is a lower bound if more indicators exist.
The archived log contributes zero IOC matches, so the recursive total is still eight, equal to the three-log Lab 9 result. Counts refer to matching indicator entries per log, not event counts or globally unique indicators.
A meaningful exit code lets a nightly scheduler raise an investigation alert automatically, while treating processing errors separately from a completed scan.
